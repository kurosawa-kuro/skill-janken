# ADR 0004: 現行ゲームに合わせたDB再設計

2026-10-26。採用。利用者の「DB設計をゼロから見直して修正」に対応する。ADR 0003のゲームルールは維持し、同ADRの物理スキーマ維持判断を本決定で更新する。

旧設計には廃止したAssets・RecipesとassetId、固定初期状態JSON、操作ごとの入力・結果・状態JSONが残った。GASの障害時の書込み境界を維持しつつ、データの事実と派生値を分離する。

物理スキーマ2はPlayers・Characters・Skills・CharacterSkills・Actions・Settingsの6表。Actionsは15個の型付き列で入力・抽選結果・同一要求識別・版・時刻・整合性ハッシュを保存し、状態や得点を重複保存しない。初期所有と最大200行から所有・スコア・対戦結果を復元する。ゲームルールはmasterVersion=2、API状態形式はschemaVersion=1のまま。

PlayerCharacters・PlayerState・PlayerSkills・Battlesを同時更新する案は、Sheetsに複数表の原子的更新がなく、固定規模に対して復旧の複雑さが増すため採らない。1人・200件を超える設計へ一般化する判断ではない。行ごとのRPCは使わず、取得後の復元はメモリーで行う。

AIセリフ管理2表のJSONは残す。最大9枠・各3文という有限の採用集を1行で公開する境界に意味があるためで、ゲーム履歴の重複JSONとは用途が異なる。生成予約と日次上限はGAS全体のScript Propertiesに残し、DBのコピー・移行で生成上限を初期化しない。

旧物理1は読取り専用。マスター2の履歴はバックアップ後に別ブックへ明示変換し、入出力・状態・識別子の一致と元データ不変を確かめる。マスター1の合成・ポイント残高は現行ルールへ読み替えない。いずれも自動切替や元データへの上書きをしない。

recordHashは誤編集検出であり、署名や所有者による改変の防止を保証しない。計算規則の変更はマスター版・移行を伴わせる。テストコードは更新するが、利用者の指示に従い検証は最後にまとめる。仕様正本は[データモデル](../05_data_model.md)。

## 画像の制作・変換・登録・配信

### 初版の制作工程

1. 提供者がキャラ3件・スキル4件の固定プロンプトを用意する。
2. [一時実行手順](08_release_runbook.md#管理関数の一時実行)で管理関数 `generateAsset_(assetId)` を実行する（末尾 `_` の関数はエディタの実行候補にも出ない）。Script PropertiesのキーとモデルIDを使い、Gemini APIを呼び出す。
3. 応答の画像パートを探す。画像がない、拒否された、429/5xxになった場合は失敗として記録し、READYにしない。
4. 返されたMIMEタイプを確認し、元画像を非公開のDriveフォルダーへ保存する。拡張子だけをWebPに変えない。
5. 提供者が元画像を取得し、手元の画像編集ソフト、またはローカルのCanvas変換ページで512×512以下のWebPへ変換する。
6. 大人が内容を確認し、採用WebPをDriveへアップロードする。
7. `registerWebp_(assetId, fileId)` でサイズ・MIME・ファイルのWebPヘッダーを検証し、AssetsをREADYにする。

画像生成対応モデルは実装日に利用可能なものを選び、`GEMINI_IMAGE_MODEL` に設定する。APIから画像データを取得する方式は[Geminiの画像生成公式資料](https://ai.google.dev/gemini-api/docs/image-generation)を確認する。アプリのゲーム仕様は特定モデルに依存させない。

2026-10-26の疎通用候補は `gemini-3.1-flash-lite-image`。既存アプリのgenerateContent方式を再利用し、[同APIの画像生成公式例](https://ai.google.dev/gemini-api/docs/generate-content/image-generation)で画像パートの取得方式を確認した。[公式料金](https://ai.google.dev/gemini-api/docs/pricing)では通常1K画像の出力が1枚0.0336米ドル、入力・テキスト出力は別料金、API無料枠なし。これは利用料金の保証や実際の請求額ではない。キーの利用可能モデル・割当は未確認で、実生成前に設定する。旧2.5 Flash Imageは同資料で終了予定日が過ぎているため採用しない。

管理関数は `https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent` を呼ぶ方式を実装し、モデルに合わせた画像出力設定を使う。キーは `x-goog-api-key` ヘッダーに入れ、URLやログに含めない。モデルごとの対応フィールドは公式資料の実装時点の例に合わせる。

自動WebP変換までGASだけで完結させることは初日の必須範囲にしない。必要なら提供者用ローカルページで `canvas.toBlob(..., 'image/webp', 0.82)` を使い、返されたBlobのMIMEタイプを確認する。WebP非対応時は別の変換手段を使う。

### プロンプト案

キャラクター共通：

> 小学生向けのじゃんけん教育ゲームのオリジナルキャラクター。［ひのこ／しずく／このは］をテーマに、親しみやすい丸い形、太い輪郭、明るい配色。正方形の中央に全身を大きく配置。背景は単色。文字、ロゴ、既存作品のキャラクター、実在人物は含めない。怖い表現を避け、同じカードシリーズとして統一する。

スキル共通：

> 同じ教育ゲームで使う正方形のスキルアイコン。［勝ちのひらめき／負けても一歩進む／あいこの輪／探究の光］を、一目で分かる1つの象徴として描く。太い輪郭、明るい配色、単色背景。文字や数字は含めない。キャラクターカードと調和する絵柄。

生成画像は表示前に提供者が確認し、採用しないものはREJECTEDにする。元プロンプトの版・モデルID・生成日時を記録する。子どもの氏名・顔写真・入力内容を生成APIに送らない。

### 配信とサイズ制約

- 採用画像は1枚100KiB以下、512×512以下を目標兼登録条件にする。7枚で合計700KiB以下。
- getAssetはAssetsの許可IDからだけDrive Blobを読み、WebPのbase64を返す。画面はdata URLとして表示する。
- base64は元バイナリより約1/3大きくなるため、初回に全画像をまとめて返さない。画面内メモリでassetId＋versionごとに保持する。
- Drive共有URLを画像配信用の公開URLとして使わない。画像が多くなる段階で専用ストレージと配信方式へ移す。
- 画像生成の試行上限は初日14回（7枚×最大2回）を目安に提供者が管理する。料金は利用モデルの現行条件で確認し、ゲームから追加課金が発生する経路は作らない。

### ③で追加したローカル変換と管理コマンド

生成元をローカルへ保存した後、`node scripts/convert-webp.mjs source.png output.webp` を実行する。PNG/JPEG/WebPをChromiumで読み、縦横比を保って長辺512px以下に縮小し、100KiB以下のWebPへ変換・再デコードする。既存出力は上書きしない。元ファイルは16MiB以下、画像は32メガピクセル以下。これは形式変換であり内容確認・Drive登録・READY化は行わない。提供者が画像を確認した後、②のregister手順で登録する。

`npm run build` 後の `node scripts/operator.mjs backup` は検証済みバックアップ、`restore BACKUP_ID` は別コピーへの復元検証、`verify` は試験用コピーだけに決定的な1行を追記して再送・バックアップ・復元を確認するエディタ専用ビルドを作る。verifyはコピー3冊を作り、元の接続先やActionsを変えない。200件に達した元データでは追加試験できない。

実行は従来どおりartifacts/operatorからclasp push、エディタのoperatorRunを1回実行する。終了後はエディタでserver/operator-run.gsを削除して通常distをpushし、存在しないことを確認する。管理ビルドからデプロイ・版作成をしない。生成HTTP 429の再試行や課金設定変更をこれらの操作に含めない。

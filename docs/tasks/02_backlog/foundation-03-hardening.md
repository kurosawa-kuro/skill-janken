# ③ 土台拡張 — 保存・再送・画像管理の共通基盤

## Goal

②で接続できた最小構成を、ゲーム機能を安全に接続できる保存・通信・画像管理の基盤へ仕上げる。

## Context

[② 連携疎通](../03_active/foundation-02-integration.md)の実環境確認が前提。[親タスク](mvp-implementation.md)の第3段階。「土台拡張」はMVPに必要な共通処理の整備を指し、複数プレイヤー化・一般公開・任意の将来拡張は含めない。実装・検証は未着手。

## Scope

- 8表の整合性検証、Actions専用の追記・状態復元、ロック、requestId・version・上限判定を実装する。
- クライアントの保留要求・手動再送・操作抑止、画像キャッシュ・代替表示を実装する。
- 提供者の生成→WebP化→確認→登録→画面表示を1枚で通す。7枚の本番素材制作は後続のMVP作業とする。
- ゲームの勝敗・得点・抽選・合成ルール、5画面、関係図、最終受入は親タスクに残す。

## Skeleton

変更処理は `入力検証 → ScriptLock → 全行の整合性確認 → requestId照合 → version・上限確認 → 状態遷移 → Actions追記 → flush → 再読込確認`。

保存処理とゲーム固有の状態遷移を分ける。先にテスト専用の決定的な状態遷移を注入して検証し、本番APIにダミー加点や疎通用変更opを作らない。後続のGameServiceがこの境界を使う。

## Plan

- [ ] 写真日記のSheets読込部品と英語トレーナーのロック保護を必要分だけ移植する。主キー空欄の非空行を捨てず、数値・真偽値の型を保持する。
- [ ] マスター、CharacterSkills 9行、R01、全Actionsの連番・一意性・JSON・状態の整合性を検証する。Actionsが0件の場合だけ初期状態を使用する。
- [ ] UUID、expectedVersion、正規化payloadとSHA-256、4KB要求・8KB JSONセルの計測方法を実装・記録する。
- [ ] 同一ID照合をversion・200件上限より先に実施する。保存済みなら同じ結果を返し、異なる入力ならREQUEST_ID_CONFLICTにする。
- [ ] 1行のsetValues→flush→再読込確認をScriptLock内で実施し、ロック待機3秒・例外時の解放・書込み後の応答喪失を検証する。
- [ ] 送信前に要求全体をsessionStorageへ保存し、同一要求の手動再送・再読込復元・再送解決後bootstrap・通信中の操作抑止を実装する。
- [ ] ②の画像経路を、WebP内容・寸法・容量・READY制約・assetId＋versionキャッシュ・名前付き代替表示まで仕上げる。
- [ ] 生成画像1枚をWebP化し、提供者の内容確認後に登録・表示する。生成拒否・画像なし・通信エラーではREADYにしない。
- [ ] テスト用コピーでバックアップ・復元手順を確認し、docs/02・04〜08に実装・運用・検証結果を反映する。

## Acceptance Criteria

- [ ] 最新Actionsが状態の正本となり、不完全行・不正参照・不正な状態遷移で停止する。黙った巻戻しや自動初期化をしない。
- [ ] 同一要求の再送で行が増えず、内容違い・version競合・200件上限を区別する。上限到達後でも保存済み要求は再取得できる。
- [ ] ロック取得失敗、flush失敗、書込み成功後の応答喪失を試験し、二重保存・二重適用を防ぐ。
- [ ] ブラウザ再読込後にも保留要求を復元でき、再送後は最新状態を表示する。保存前の成功演出をしない。
- [ ] Gemini生成元から採用WebP1枚まで通り、512×512以下・100KiB以下・非公開・READYを満たす。
- [ ] 画像失敗で遊びの継続を妨げず、試験用コピーの復元後に保存状態と版が一致する。
- [ ] ゲーム実装へ渡すサービス境界・実コマンド・既知の制約が記録されている。

## Verification

未実施。単体・モック結合、ブラウザ状態復元、実GAS＋試験用Sheets/Driveの確認を区別して記録する。外部障害を実際に大量発生させず、失敗経路はモックや試験用の内部注入で確認する。

保存試験の状態遷移はテスト専用であり、ゲーム固有の勝敗・ポイント・合成検証の合格とは扱わない。対応する[AC](../../07_test_strategy.md)には、部分確認と未確認範囲を明記する。

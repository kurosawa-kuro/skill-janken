# ③ 土台拡張 — 保存・再送・画像管理の共通基盤

## Goal

②で接続できた最小構成を、ゲーム機能を安全に接続できる保存・通信・画像管理の基盤へ仕上げる。

## Context

[② 連携疎通](foundation-02-integration.md)ではSheets・Driveを実測済み。Gemini画像生成はHTTP 429、提供者は無料プラン／未確認。2026-10-26の「次進んで」に基づき、課金に依存しない基盤を先行する。[親タスク](../02_backlog/mvp-implementation.md)の第3段階。「土台拡張」はMVPに必要な共通処理の整備を指し、複数プレイヤー化・一般公開・任意の将来拡張は含めない。保存・再送・コピー復元とローカル変換を実装。画像生成から採用までの確認を残すため完了扱いにしない。

## Scope

- 8表の整合性検証、Actions専用の追記・状態復元、ロック、requestId・version・上限判定を実装する。
- クライアントの保留要求・手動再送・操作抑止、画像キャッシュ・代替表示を実装する。
- 提供者の生成→WebP化→確認→登録→画面表示を1枚で通す。7枚の本番素材制作は後続のMVP作業とする。
- ゲームの勝敗・得点・抽選・合成ルール、5画面、関係図、最終受入は親タスクに残す。

## Skeleton

変更処理は `入力検証 → ScriptLock → 全行の整合性確認 → requestId照合 → version・上限確認 → 状態遷移 → Actions追記 → flush → 再読込確認`。

保存処理とゲーム固有の状態遷移を分ける。先にテスト専用の決定的な状態遷移を注入して検証し、本番APIにダミー加点や疎通用変更opを作らない。後続のGameServiceがこの境界を使う。

- [x] 送信前に要求全体をsessionStorageへ保存し、同一要求の手動再送・再読込復元・再送解決後bootstrap・通信中の操作抑止を実装する。

## Acceptance Criteria

- [x] 最新Actionsが状態の正本となり、不完全行・不正参照・不正な状態遷移で停止する。黙った巻戻しや自動初期化をしない。
- [x] 同一要求の再送で行が増えず、内容違い・version競合・200件上限を区別する。上限到達後でも保存済み要求は再取得できる。
- [x] ロック取得失敗、flush失敗、書込み成功後の応答喪失を試験し、二重保存・二重適用を防ぐ。
- [x] ブラウザ再読込後にも保留要求を復元でき、再送後は最新状態を表示する。保存前の成功演出をしない。
- [ ] Gemini生成元から採用WebP1枚まで通り、512×512以下・100KiB以下・非公開・READYを満たす。
- [x] 画像失敗でも土台画面の記録・名前表示が続き、試験用コピーの復元後に保存状態と版が一致する。ゲーム画面の継続確認は後続。
- [x] ゲーム実装へ渡すサービス境界・実コマンド・既知の制約が記録されている。

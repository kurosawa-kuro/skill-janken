# 01 要件 — スキルじゃんけんラボ

反映日：2026年10月26日。初期資料（退避済み）：[01_企画書.md](archive/スキルじゃんけんラボ_企画・仕様・設計/01_企画書.md)・[02_仕様書.md](archive/スキルじゃんけんラボ_企画・仕様・設計/02_仕様書.md)（v1.0）。

本書は提案仕様をプロジェクト用に整理した設計文書。アプリ実装・受入試験・公開は未完了であり、実績や試験合格を示さない。参照元と本書の役割・更新規約は[索引](00_index.md)を参照。

## 目的

提供者本人が、まず「遊べて、仕組みを見せられるゴールアプリ」を1日程度で作る。その完成物を教材づくり・子どもへの試遊・将来のサービス検討の出発点にする。最初から教材販売基盤や大規模ゲーム運営を作らない。

子どもがキャラクターを集め、スキルを選び、じゃんけんをして、決まった組み合わせから新しいスキルを発見する。遊びの裏にある「1人に複数の記録」「1体に複数のスキル／1つのスキルを複数のキャラクターが使う」を可視化し、1対多・多対多のリレーションを学ぶ入口にする。

将来のECサイトの「顧客と注文」、管理画面の「ユーザーと役割」へつながる理解を目指す。初回からSQLや正規化の用語を覚えさせることは目的にしない。

以下の根拠の記述は企画書から引き継いだもの。本監査で参照チャットを再取得・再確認したものではない。

参照チャットから確認できた要望は、提供者が先にゴールアプリを作ること、1日程度という開発感覚、GASアプリへのスキル合成・Geminiイラストの紐付け、WebP表示、1対多・多対多の学習、巨大・複雑にしないことである。参照チャットの過去のアシスタント本文は取得結果に含まれなかったため、過去に詳細仕様が合意済みとは扱わない。

以下は今回の設計提案であり、ユーザーの過去の確定発言ではない。

| 項目 | 初版の前提 |
|---|---|
| 対象 | 小学校中〜高学年を仮対象。大人が伴走する |
| 提供形態 | 提供者自身のGoogleアカウントで開く、管理端末上の試遊 |
| プレイヤー | 仮名のデモプレイヤー1人。交代して遊ぶ場合は同じ記録を使う |
| 端末 | スマートフォンの縦画面を中心とするWebアプリ |
| 開発者 | GAS・JavaScript・Sheetsの基本を扱える提供者1人 |
| 1日の意味 | 準備済みアカウントと利用可能な画像生成環境があり、約8時間を使える目標値 |
| 画像生成 | 大人が事前に生成・確認。遊ぶたびに生成しない |
| 公開範囲 | 初版は本人限定。子どもが各自の端末から参加する公開サービスは次段階 |

本人限定公開は、独立した子どもアカウント・認証・同意管理を1日に詰め込まないための設計判断。提供者アカウントの認証情報を子どもに配布せず、管理端末でアプリだけを見せる。

## MVPの範囲

| 初日に必ず完成するもの | 内容 |
|---|---|
| キャラクター | 3体。最初に1体、残り2体を無料抽選で獲得 |
| スキル | 基本3種、合成1種。装備は1回の勝負につき1つ |
| 対戦 | CPUとの1手完結じゃんけん。HP・属性相性・ターン制なし |
| 合成 | 基本スキル2つから1つの上位スキルを解放する固定レシピ1件 |
| 保存 | 所有・ポイント・合成結果・行動記録をSheetsに保存 |
| イラスト | Geminiで作った採用画像をDriveに置き、WebPを表示 |
| 学習 | 1対多の記録一覧、多対多のキャラ―スキル対応表 |
| 運用 | 本人限定公開、二重実行対策、画像失敗時の代替表示、バックアップ手順 |

初日に作らないもの：課金、広告、対人戦、ランキング、チャット、ユーザー登録、自由入力プロンプト、子どもによる画像生成、無限合成、生成AIによるゲーム効果決定、リアルタイム同期、教材販売、保護者管理画面。


初版は1端末・P001の1プレイヤー・同時変更1件・成功した行動記録200件までの短期デモ。一般公開、学校全体での同時利用、独立した子どもアカウントは対象外。

## 子どもが体験する価値

1. 「なかまをよぶ」で新しいイラストカードが出る。
2. キャラクターとスキルを1つずつ選ぶ。
3. グー・チョキ・パーを押して、CPUと1回勝負する。
4. 勝敗とスキルによって探究ポイントが増える。
5. 3ポイントで固定レシピを試し、新しいスキルを覚える。
6. 「つながりをみる」で、同じスキルが複数の仲間につながることに気づく。

負けても基本ポイントを得られる。スキルは勝敗を書き換えず、ポイントにだけ作用するため、じゃんけんの理解を妨げない。

| F06 | 画像表示・代替 | 採用WebPを表示し、画像失敗時も遊びを継続 | AC16、AC17 |

## Critical User Journey / Golden Path

一次ユーザーは大人と管理端末で試遊する子ども。仲間獲得から合成スキルの使用・学習表示までを完走し、再読込後も結果が残ることを完成状態とする。新規デモデータで開始する。

| # | ステップ | 成功条件（観測可能な状態） |
|---|---|---|
| 1 | 本人限定URLで起動 | P001、C01、S01〜S03、0ポイント、version 0 |
| 2 | 「なかまをよぶ」を2回 | 重複なしで全3体。次の抽選は無効 |
| 3 | C01とS01を選び、じゃんけん | 勝敗と基本点・加算が表示され、保存される。合計3ポイント以上になるまで繰り返す |
| 4 | S01＋S02を合成 | 3ポイントを1回だけ消費し、材料を残してS04習得 |
| 5 | S04を選んでじゃんけん | 勝敗を変えず、いずれの結果でも基本点に+1 |
| 6 | 「つながり」を見る | 実記録の最新10件とCharacterSkillsの9本の関連。S04の鍵だけが外れる |
| 7 | 再読込・再開 | 保存済みversion・ポイント・所有・習得が一致 |

構成要素との対応は[アーキテクチャ](02_architecture.md)、実機での確認手順は[リリース手順](08_release_runbook.md)、合否の詳細は[テスト戦略](07_test_strategy.md)を参照する。

## 学習体験

| 学習テーマ | ゲーム内で見るもの | 大人が添える問い | 業務アプリへの接続 |
|---|---|---|---|
| 1対多 | 1人のプレイヤーに複数の行動記録 | 「この人の記録は何件ある？」 | 顧客1人と複数の注文 |
| 多対多 | キャラクター3体とスキル4種の対応表 | 「このスキルを使える仲間は何体？」 | ユーザーと役割、商品とカテゴリ |
| 中間テーブル | CharacterSkillsの1行が1本の線 | 「仲間の表にスキル名を全部詰めたらどうなる？」 | 関連付けを独立した表にする |
| 参照の一貫性 | 名前を変えてもIDの線は変わらない | 「同じ名前が2つあったら？」 | 主キー・外部キーの入口 |
| 固定ルール | レシピに一致すると結果が決まる | 「材料の順番を逆にしたら？」 | 入力検証・業務ルール |

子どもが遊ぶ段階では短い言葉と絵を優先する。大人と仕組みを見る段階でIDや表名を表示する。キャラクター間のバトルを「多対多」と呼ぶのではなく、データの対応関係を学ぶ。

## 画面・アクセシビリティ

5画面＋結果モーダルで構成する。下部に「ホーム／なかま／じゃんけん／ごうせい／つながり」を配置する。

| ID | 画面 | 主な表示 | 操作と遷移 |
|---|---|---|---|
| UI01 | ホーム | 仲間の絵、ポイント、現在の仲間、次の遊びの案内 | 抽選ボタン、各画面への移動、再読込 |
| UI02 | なかま | 3体のカード、所有状態、使えるスキル | 所有カードを選択→じゃんけん。未所有は選べない |
| UI03 | じゃんけん | 選択仲間、スキル選択、3つの手ボタン | 手を押す→待機→結果モーダル。「もういちど」または閉じる |
| UI04 | ごうせい | 材料2枠、結果プレビュー、必要ポイント | 条件がそろえば合成→結果モーダル |
| UI05 | つながり | 記録一覧、キャラ×スキル対応表、仕組み説明 | 表の行・列を選択して対応を強調 |

通信中はすべての状態変更操作を無効にする。戻る操作は表示の切替だけで、送信済み要求を取り消さない。画面再表示時はサーバー状態を取得する。

### UIの共通条件

- 360px幅の縦画面で横スクロールを生じさせない。対応表は省略名と詳細表示で収める。
- 主ボタンのタップ領域は縦横44px以上、本文は原則16px以上。
- 絵を主役にし、説明は短い日本語。難しい用語は学習欄だけで補足する。
- 色だけで勝敗や所有を表現しない。文字・記号を併用する。
- 画像には代替テキスト。ボタンに読み上げ可能な名前。結果・エラーは読み上げ通知する。
- 音声は初版なし。動きを減らす端末設定では演出を省略する。
- パソコンではキーボードでボタンを選択でき、結果を閉じたら操作元へフォーカスを戻す。

## 完成の定義

- スマートフォンで、仲間獲得→装備選択→じゃんけん→合成→合成スキルを使用、を完走できる。
- ポイントと所有状態が再読込後も維持され、同じ要求の再送で二重加算されない。
- キャラクター3枚・スキル4枚の採用画像を表示でき、画像失敗時も操作を続けられる。
- 学習画面の表示がSheetsの実データと一致する。
- 提供者本人以外のGoogleアカウントからアクセスできないことを確認する。
- 仕様書由来の受入条件と結果は[テスト戦略](07_test_strategy.md)に記録する。本文書は設計成果物であり、アプリの実装・試験完了を示すものではない。

## 試遊で観察すること

初回は提供者の説明付きで5〜10分。子どもの氏名・年齢・写真は記録せず、「次に押す場所が分かったか」「合成後の変化を説明できたか」「同じスキルが複数の仲間につながることに気づいたか」を提供者がメモする。

学習効果や継続率を保証する企画ではない。試遊を通して、楽しさとリレーションの理解が両立するかを確かめる。

## 運用と将来拡張の優先順

初版の想定は1端末・1プレイヤー・同時操作1件、行動記録200件までの短期デモ。一般公開や学校全体での同時利用は対象外。

次段階の優先順は、①複数のデモデータで教材を作る、②安全な個別認証とプレイヤー分離、③教室での限定運用、④必要になった場合のDB・画像配信基盤への移行。公開前には対象者、同意・削除の流れ、利用規約、利用するGoogleサービスの条件、問い合わせ窓口を具体的な運用に合わせて確認する。

「画像を毎回生成する」「無限のスキルを作る」は利用料金・待ち時間・内容確認・効果の整合性を増やすため、初版完成の後で別機能として判断する。

## 仕様変更の境界

キャラ・スキル・レシピを増やす場合は、ID参照、適性、確率表示、画像、受入条件を一緒に更新する。対戦効果は定義済み効果コードだけを扱い、Sheetsの任意コードやAI出力を実行しない。

複数プレイヤー、子ども本人によるログイン、公開アクセス、リアルタイム生成は本書の範囲外。初版の公開設定を緩めるだけでは対応できない。

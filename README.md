# スキルじゃんけんラボ

仲間を集め、スキルを選んでCPUとじゃんけんし、固定レシピから新しいスキルを発見する教育用Webアプリです。遊びの記録とキャラクター・スキルの対応表を通じて、データの「1対多」「多対多」のつながりを学ぶ入口を作ります。

**①完了、②の外部確認を残して③土台拡張を進めています。** ①土台作成は完了。②ではSheetsの8表初期化・読込、非公開Driveの検証とWebP登録・取得、Gemini画像生成用アダプターを実装した。専用GASの本人限定試験配置で初期記録の表示と再読込を確認済み。テスト用WebPの実配信を確認済み。Geminiの認証・モデル一覧取得は成功したが画像生成はHTTP 429。提供者から無料プラン／未確認との回答があり、課金・割当の確認待ち。別アカウント拒否は未確認。ゲーム機能・最終受入は未完了。③ではActions追記・最新状態復元・同一要求の再送・保留要求の復元・画像キャッシュ・検証付きバックアップコピーを実装した。ゲームの変更APIと5画面は後続。③の画像生成から採用までの確認は②のGemini HTTP 429解消待ち。以下の体験は初版の完成時の仕様です。

## 初版の体験と範囲

1. 「なかまをよぶ」で、未所有の仲間を無料で獲得する。
2. 所有する仲間1体と、その仲間が使えるスキル1つを選ぶ。
3. グー・チョキ・パーを押し、CPUと1手で勝負する。
4. 探究ポイントを3ポイント使い、固定レシピで新スキルを習得する。
5. 合成したスキルで遊び、「つながり」で記録やスキルの対応を見る。

| 項目 | 初版の設計 |
|---|---|
| 対象 | 小学校中〜高学年を仮対象とし、大人が伴走 |
| 利用形態 | 提供者の管理端末、本人限定公開、縦画面スマートフォン中心 |
| プレイヤー | P001「たんけんたい」1人。交代時も同じ記録を使用 |
| 仲間 | C01「ひのこ」、C02「しずく」、C03「このは」の3体 |
| 抽選 | 最初はC01を所有。残り2体を未所有から等確率・重複なしで獲得 |
| スキル | 基本3種＋合成1種。1回の対戦で装備するのは1つ |
| ポイント | 勝ち2点、あいこ・負け1点。スキルの条件を満たすと+1 |
| 合成 | S01＋S02→S04、順不同、3ポイント消費、材料は残る、解放は1回 |
| 画面 | ホーム／なかま／じゃんけん／ごうせい／つながり＋結果モーダル |
| 保存 | 所有・習得・ポイント・行動記録。成功した変更は200件まで |
| 画像 | Geminiで事前制作したキャラ3枚＋スキル4枚の採用WebP |

初期状態はC01所有、S01〜S03習得、0ポイント、version 0です。S01「かちのひらめき」は勝ち、S02「まけてもいっぽ」は負け、S03「あいこのわ」はあいこ、S04「たんきゅうのひかり」はすべての結果で+1になります。スキルはポイントにだけ作用し、勝敗を変えません。

「習得」はプレイヤー全体の解放状態、「適性」はキャラクターとスキルの対応です。使用には両方を満たす必要があります。合成でS04を習得しても、適性を表す `CharacterSkills` の9行は変わりません。

初版の対象外は、課金、広告、対人戦、ランキング、チャット、ユーザー登録、複数プレイヤー、一般公開、自由入力プロンプト、子どもによる画像生成、遊び中の画像生成、無限合成、AIによるゲーム効果決定、リアルタイム同期、教材販売、保護者管理画面です。

## 学べるデータのつながり

| テーマ | アプリ内の表示 |
|---|---|
| 1対多 | 1人のPlayersにひも付くActionsの最新10件。対戦だけの絞り込みも可能 |
| 多対多 | Characters 3体とSkills 4種を結ぶCharacterSkillsの対応表 |
| 中間テーブル | 対応表の1行が1本のつながりになることを、キャラ・スキルの選択で強調 |
| IDによる参照 | 「しくみの名前」で表名とIDを確認 |

学習画面はAPIから取得した実データで組み立てます。S04の適性線は合成前から表示し、合成後は「まだおぼえていない」の鍵だけが外れます。

## 技術と保存設計

| 技術 | 役割 |
|---|---|
| Google Apps Script（GAS / JavaScript） | HTML Serviceによる画面配信、入力検証、勝敗・ポイント計算、保存 |
| HTML / CSS / JavaScript | スマホ向け5画面、カード、結果表示、学習画面 |
| Google Sheets | 8シートのマスター・初期状態・行動記録 |
| Google Drive | 非公開の元画像・採用WebP・バックアップ保管 |
| Gemini | 提供者がキャラクターとスキルの画像を事前制作 |

画面は `doGet()` が配信し、`google.script.run` から `api(request)` を呼びます。操作は `bootstrap`、`drawCharacter`、`playRound`、`synthesize`、`getRelations`、`getAsset` の6つです。独立したRESTサーバーや別ホスティングは初版に含めません。

Sheetsには `Players`、`Characters`、`Skills`、`CharacterSkills`、`Recipes`、`Assets`、`Actions`、`Settings` を置きます。成功した変更ごとに入力・結果・次状態をActionsへ1行追記し、最新行の `stateJson` を現在状態とします。行が0件のときだけPlayersの初期状態を使い、現在状態を別表へ二重保存しません。

`ScriptLock`、`requestId`、`expectedVersion` で排他・再送・競合を扱います。同じ要求の再送は保存済みの結果を返し、抽選・加減算を繰り返しません。不完全行や参照不整合では変更を止め、自動で初期化しません。SheetsにDB同等のトランザクションを保証させる設計ではありません。

## 開発の準備

Node.js 22以上を用意し、プロジェクトルートで実行します。

```powershell
npm ci
npx playwright install chromium
npm run check
npm run preview
```

Chromiumが導入済みならインストールは不要です。プレビューは `http://127.0.0.1:4173/` の仮データ表示で、Ctrl+Cで終了します。`npm run check` は整形確認・40件のローカルテスト・ビルド・ブラウザ確認を行います。`npm run build` の出力はdistで、アップロードやデプロイはしません。Makefileはnpmのラッパーです。

③の保存・再送・復元基盤を実装し、本人限定Web版をv2へ更新しました。②③に残る画像生成の確認を追跡しつつ、次の実装対象はゲームルール・5画面です。[開発手順](docs/04_workflows.md)、[API契約](docs/02_architecture.md)、[初期データ・保存](docs/05_data_model.md)、[配置・復旧](docs/08_release_runbook.md)を参照してください。進捗は[MVP親タスク](docs/tasks/02_backlog/mvp-implementation.md)で追跡します。

1. 提供者のGoogleアカウントで、GAS・Sheets・非公開Driveフォルダーと画像生成環境を準備する。
2. GASのScript PropertiesにSpreadsheet ID、DriveフォルダーID、Gemini APIキー、画像モデルIDを設定する。キーをHTML・Sheets・ブラウザ保存領域・ログに置かない。
3. マスター検証、勝敗・ポイント・レシピの純粋関数、保存・再送処理を実装する。
4. 5画面、画像制作・配信、実データの学習画面をつなぐ。
5. 本人限定設定で配置し、受入条件・実機操作・バックアップ復元を確認する。

`env/` と `doppler.yaml` は既存の開発用ひな形です。GASへの設定同期は未実装で、初版の実行時設定はScript Propertiesを使います。ローカル秘密情報をコミットしません。画像生成モデル・料金・公開設定・サービスの割当は実装時に公式資料で確認します。

## 画像・公開・運用

- 画像は提供者が生成し、WebPへの変換と内容確認を経て登録します。1枚512×512以下・100KiB以下、7枚合計700KiB以下とし、ゲーム中にGeminiを呼びません。
- `getAsset` は許可されたREADY画像を1枚ずつbase64で返します。Drive共有URLは配信に使わず、画像失敗時は図形と名前の代替表示で遊びを継続します。
- GASは実行ユーザー「自分」、アクセス範囲「自分のみ」に相当する設定とし、Sheets・Driveも非公開にします。子どもには管理端末上でアプリを見せ、提供者の認証情報は渡しません。
- デモ前後とマスター変更前にSheetsをコピーします。200件到達時は提供者が記録を保管して初期化し、端末の保留要求を消してタブを開き直します。復旧はテスト用コピーで検証します。
- 試遊では子どもの氏名・年齢・写真を記録せず、記録は原則30日で見直します。一般公開や個別プレイヤーへの拡張は別途設計します。
